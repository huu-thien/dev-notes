# Amazon EC2

Elastic Compute Cloud (EC2) — dịch vụ compute nền tảng, cung cấp virtual machine (instance) có thể tuỳ chỉnh cấu hình, hệ điều hành, và mạng.

## Practical understanding

### EC2 là gì

**Amazon EC2** cung cấp virtual server (instance) chạy trên hạ tầng AWS, cho phép kiểm soát gần như toàn bộ OS, runtime, và ứng dụng bên trong — khác với các managed/serverless compute (Lambda) nơi AWS quản lý phần hạ tầng bên dưới.

🧠 **Exam mindset:** EC2 giải quyết bài toán "cần một máy chủ tôi kiểm soát được (OS, runtime, network) để chạy ứng dụng theo cách tôi muốn". Nếu đề mô tả nhu cầu ngược lại — "không muốn quản lý server", "chỉ chạy code khi có sự kiện", "chi phí theo request thực tế" — đó là tín hiệu rời khỏi EC2 sang Lambda/Fargate.

### Instance families (mức đủ cho SAA-C03)

Không cần nhớ chi tiết từng loại, chỉ cần nắm nhóm chính và mục đích:

| Nhóm | Mục đích chính |
|---|---|
| General Purpose (VD: `t`, `m`) | Cân bằng compute/memory/network, phù hợp workload đa dụng (web server, dev/test) |
| Compute Optimized (VD: `c`) | Ứng dụng cần CPU cao: batch processing, gaming server, video encoding |
| Memory Optimized (VD: `r`, `x`) | Ứng dụng cần RAM lớn: in-memory database, cache lớn, real-time big data |
| Storage Optimized (VD: `i`, `d`) | Ứng dụng cần I/O disk cao: NoSQL database, data warehousing |

> Cần verify lại theo AWS official docs mới nhất — tên và số lượng instance family thay đổi thường xuyên.

🧠 **Instance family selection mindset:** đề thi hiếm khi hỏi tên instance cụ thể, mà hỏi **triệu chứng workload** để suy ra nhóm:

- "CPU luôn ở mức cao, xử lý tính toán nặng" → Compute Optimized.
- "cần giữ toàn bộ dataset trong RAM, truy vấn cực nhanh" → Memory Optimized.
- "đọc/ghi disk liên tục với throughput cao" → Storage Optimized.
- "không có tín hiệu đặc biệt nào, workload web/app thông thường" → General Purpose (lựa chọn mặc định an toàn khi đề không nhấn mạnh đặc điểm nào).

### Purchasing options (áp dụng cho EC2)

Xem chi tiết ở [../01-foundation/04-pricing-and-billing-basics.md](../01-foundation/04-pricing-and-billing-basics.md); tóm tắt áp dụng riêng cho EC2:

| Option | Phù hợp với |
|---|---|
| On-Demand | Workload ngắn hạn, không dự đoán được, thử nghiệm |
| Reserved Instances | Workload ổn định, chạy liên tục 1-3 năm |
| Savings Plans | Tương tự Reserved nhưng linh hoạt hơn về instance family/Region |
| Spot Instances | Workload chịu được gián đoạn (batch, stateless, fault-tolerant) |

🧠 **Cost vs flexibility trade-off:** thứ tự đánh đổi giữa các option luôn theo 1 trục — càng cam kết dài hạn/ổn định (Reserved/Savings Plans), giá càng rẻ nhưng càng kém linh hoạt; càng linh hoạt (On-Demand), giá càng cao. Spot nằm ngoài trục này — rẻ nhất nhưng đánh đổi bằng **rủi ro bị thu hồi bất kỳ lúc nào**, không phải đánh đổi về cam kết thời gian.

- ✅ Chọn Spot khi: workload có thể chịu gián đoạn, có checkpoint hoặc queue để resume công việc dở dang (batch job, rendering, xử lý dữ liệu song song).
- ❌ Không chọn Spot khi: production database, workload real-time không chấp nhận downtime bất kỳ lúc nào.

### AMI (Amazon Machine Image)

Template chứa OS, cấu hình, và phần mềm cài sẵn để khởi tạo instance. Có thể dùng AMI của AWS, của cộng đồng, hoặc tự tạo AMI riêng (custom AMI) để chuẩn hoá việc triển khai nhiều instance giống nhau.

🧠 **AMI reasoning:** khi đề mô tả "cần khởi tạo nhiều instance giống hệt nhau nhanh chóng, đã cài sẵn phần mềm/cấu hình", đáp án luôn xoay quanh **custom AMI** (golden image) kết hợp Auto Scaling — không phải cài đặt thủ công lặp lại qua User Data mỗi lần.

### Security Group (áp dụng cho EC2)

**Security Group** là firewall stateful gắn trực tiếp vào instance (qua ENI), chỉ có rule allow, đánh giá theo default-deny. Đây là lớp bảo vệ đầu tiên và bắt buộc phải cấu hình đúng theo nguyên tắc **Least Privilege** — chỉ mở đúng port/nguồn cần thiết. Định nghĩa đầy đủ và so sánh với NACL xem ở [`06-vpc.md`](./06-vpc.md).

### ENI (Elastic Network Interface)

Network interface ảo có thể gắn vào instance, mang theo private IP, public IP (tuỳ chọn), và Security Group riêng. Một instance có thể có nhiều ENI — hữu ích khi cần tách biệt traffic quản trị và traffic ứng dụng, hoặc khi failover ENI giữa các instance.

### Instance Store vs EBS (góc nhìn từ EC2)

- **Instance Store**: ổ đĩa vật lý gắn trực tiếp với host, tốc độ rất cao nhưng **ephemeral** — mất dữ liệu khi instance stop/terminate/di chuyển host.
- **EBS**: ổ đĩa mạng (network-attached), tồn tại độc lập với vòng đời instance, hỗ trợ snapshot.

- ✅ Instance Store phù hợp khi: cần throughput/IOPS cực cao cho dữ liệu **tạm thời**, có thể tái tạo lại (cache tầng ứng dụng, buffer xử lý tạm, scratch data của batch job).
- ❌ Instance Store không phù hợp khi: dữ liệu cần tồn tại sau khi instance restart/terminate (database file, dữ liệu người dùng quan trọng) — bắt buộc dùng EBS (hoặc S3 cho dữ liệu không cần mount).

Chi tiết đầy đủ về EBS ở [02-ebs-efs-fsx.md](./02-ebs-efs-fsx.md).

### Placement Groups

Cách kiểm soát vị trí vật lý của instance trong hạ tầng AWS:

| Loại | Mục đích |
|---|---|
| Cluster | Đặt instance gần nhau, độ trễ network thấp nhất — phù hợp HPC, big data |
| Spread | Đặt instance tách biệt trên phần cứng khác nhau — giảm rủi ro lỗi đồng thời |
| Partition | Nhóm instance theo partition riêng biệt phần cứng — phù hợp workload phân tán lớn (Hadoop, Cassandra) |

- ✅ Dùng khi: đề nhấn mạnh "độ trễ network thấp nhất giữa các instance" (Cluster), hoặc "muốn giảm rủi ro nhiều instance cùng lỗi vì chung phần cứng" (Spread), hoặc "framework phân tán tự quản lý replica theo rack" (Partition).
- ❌ Không cần dùng khi: đề không có yêu cầu đặc biệt về vị trí vật lý — placement group mặc định không mang lại lợi ích và có thể giới hạn khả năng thay đổi instance type linh hoạt (đặc biệt Cluster).

### User Data (mức cơ bản)

Script (thường là shell script) chạy tự động khi instance khởi động lần đầu — dùng để cài đặt phần mềm, cấu hình ban đầu mà không cần đăng nhập thủ công. Không dùng để lưu secret nhạy cảm (nội dung có thể đọc được qua metadata).

## Decision logic

| Câu hỏi cần trả lời | Chỉ báo trong đề (🧠 nghĩ tới EC2) | Chỉ báo loại EC2 (⚠️ cân nhắc alternative) |
|---|---|---|
| Cần kiểm soát OS/runtime/kernel đặc thù? | "custom OS/driver", "phần mềm legacy cài trực tiếp" | "chỉ cần chạy code, không quan tâm hạ tầng" → Lambda/Fargate |
| Workload chạy liên tục hay ngắn hạn theo sự kiện? | "chạy 24/7", "ứng dụng thường trực" | "chạy theo sự kiện, ngắn hạn" → Lambda |
| Traffic ổn định hay biến động mạnh không dự đoán? | "tải ổn định, dự đoán được" → Reserved/Savings Plans | "tải biến động mạnh, khó dự đoán" → cân nhắc Auto Scaling + On-Demand/Spot mix |
| Có chấp nhận gián đoạn để đổi lấy giá rẻ không? | "batch job chịu được gián đoạn" → Spot | "không chấp nhận downtime bất kỳ lúc nào" → loại Spot |
| Dữ liệu ghi ra có cần tồn tại sau khi instance dừng? | "dữ liệu tạm, có thể tái tạo" → Instance Store | "dữ liệu cần bền vững" → EBS |

## Exam focus

### Must know for exam

- Chọn purchasing option đúng theo đặc tính workload (xem bảng trên).
- Instance Store mất dữ liệu khi instance dừng — không dùng cho dữ liệu cần bền vững.
- Security Group là stateful, default-deny, chỉ có allow rule.
- EC2 phù hợp khi cần kiểm soát toàn bộ OS/runtime; nếu chỉ cần chạy code theo sự kiện, ngắn hạn → cân nhắc Lambda.

### Important

- Placement Group loại Cluster tối ưu latency, Spread tối ưu tính sẵn sàng.
- ENI có thể tách rời khỏi instance để failover nhanh giữa các instance.
- AMI custom giúp chuẩn hoá triển khai nhiều instance giống nhau (golden image).

### Nice to know

- Chi tiết cấu hình OS bên trong instance (patching, package manager) không thuộc phạm vi thi SAA-C03.

## Use cases

- Web application server cần kiểm soát toàn bộ runtime/OS.
- Ứng dụng legacy yêu cầu cài đặt phần mềm đặc thù không chạy được trên serverless.
- Batch processing dùng Spot Instances để tối ưu chi phí.
- Workload cần custom AMI để triển khai nhất quán trên nhiều instance.

## Khi nào nên dùng / không nên dùng

### Khi nào EC2 phù hợp hơn Lambda hoặc container-based options

| Tiêu chí | EC2 phù hợp hơn khi |
|---|---|
| Thời gian chạy | Ứng dụng chạy liên tục, dài hạn (không phù hợp giới hạn timeout của Lambda) |
| Kiểm soát hạ tầng | Cần tuỳ chỉnh OS, kernel, driver đặc thù |
| Ứng dụng legacy | Phần mềm không đóng gói được thành container hoặc function nhỏ |

### Compute alternatives (giới thiệu ngắn — ECS/Fargate)

**ECS (Elastic Container Service)** và **Fargate** là các lựa chọn compute chạy ứng dụng dưới dạng container:
- **ECS trên EC2**: bạn vẫn quản lý EC2 instance làm host cho container, kiểm soát hạ tầng nhiều hơn nhưng tốn công vận hành hơn.
- **Fargate**: serverless cho container — AWS quản lý toàn bộ hạ tầng bên dưới, bạn chỉ định nghĩa task/container.

Khi nào cân nhắc ECS/Fargate thay vì EC2 trực tiếp: ứng dụng đã đóng gói dạng container, muốn giảm gánh nặng quản lý OS/patching so với EC2, nhưng vẫn cần chạy dài hạn hơn giới hạn của Lambda. Nội dung so sánh đầy đủ EC2 vs ECS/Fargate vs Lambda xem ở [`../04-comparison-guides/04-lambda-vs-ecs-vs-ec2.md`](../04-comparison-guides/04-lambda-vs-ecs-vs-ec2.md).

## Anti-patterns / lựa chọn sai thường gặp

| Anti-pattern | Vì sao nghe hợp lý | Vì sao vẫn sai |
|---|---|---|
| ❌ Chọn EC2 cho workload event-driven, chạy ngắn (VD: xử lý file khi upload) | EC2 quen thuộc, kiểm soát được mọi thứ | Phải chạy 24/7 chờ sự kiện dù phần lớn thời gian idle — tốn chi phí và công vận hành so với Lambda chỉ tính phí khi có sự kiện thực tế |
| ❌ Chọn Spot cho workload không chịu được interruption (production database, real-time transaction) | Spot rẻ hơn On-Demand đáng kể | Spot có thể bị thu hồi bất kỳ lúc nào với cảnh báo rất ngắn — workload cần uptime liên tục sẽ gặp downtime ngoài kế hoạch, rủi ro mất dữ liệu/giao dịch |
| ❌ Dùng Instance Store cho dữ liệu cần bền vững (file người dùng, database chính) | Instance Store nhanh hơn EBS đáng kể | Dữ liệu mất hoàn toàn khi instance stop/terminate/di chuyển host — chỉ phù hợp dữ liệu tạm, có thể tái tạo |
| ❌ Over-provisioning (chọn instance lớn, số lượng cố định nhiều) vì không tin tưởng/không hiểu Auto Scaling | Muốn "chắc chắn" luôn đủ capacity, tránh rủi ro thiếu tài nguyên | Tốn chi phí cho capacity không dùng tới phần lớn thời gian — Auto Scaling (kết hợp CloudWatch alarm) mới là cách chuẩn để vừa đảm bảo capacity vừa tối ưu chi phí theo tải thực tế (xem [08-elb-and-auto-scaling.md](./08-elb-and-auto-scaling.md)) |

## Common traps

### ⚠️ Trap: nghĩ Spot Instance phù hợp cho mọi loại workload muốn tiết kiệm chi phí
Spot có thể bị thu hồi bất kỳ lúc nào — chỉ phù hợp workload chịu được gián đoạn. Đề hỏi "production database cần chạy liên tục, tối ưu chi phí" không nên chọn Spot.

### ⚠️ Trap: nhầm Instance Store là lựa chọn lưu trữ bền vững
Instance Store mất dữ liệu khi instance dừng/terminate — không dùng cho dữ liệu cần **Durability** cao, phải dùng EBS (hoặc S3) cho mục đích đó.

### ⚠️ Trap: mở toàn bộ port trong Security Group "cho chắc"
Vi phạm nguyên tắc **Least Privilege**. Đề thi thường có đáp án sai kiểu mở `0.0.0.0/0` cho mọi port — chỉ đúng khi thực sự cần public toàn bộ (hiếm khi là đáp án đúng).

## Mini scenarios

🧪 **Scenario 1 — Workload ổn định dài hạn, không chấp nhận gián đoạn**

**Tình huống:** Ứng dụng cần chạy liên tục 24/7 trong 2 năm tới, cấu hình ổn định, muốn tối ưu chi phí compute nhất mà vẫn đảm bảo capacity luôn sẵn sàng (không chấp nhận bị thu hồi).
**Đáp án đúng:** Mua Reserved Instances (hoặc Savings Plans) cho loại instance phù hợp.
**Vì sao:** Workload ổn định, dài hạn, không chấp nhận gián đoạn → loại Spot ngay; Reserved/Savings Plans cho giá tốt hơn On-Demand mà vẫn đảm bảo capacity.

🧪 **Scenario 2 — Chuẩn hoá triển khai nhiều instance giống nhau khi scale**

**Tình huống:** Đội vận hành cần triển khai nhanh 20 instance giống hệt nhau (cùng OS, cùng phần mềm đã cấu hình sẵn) khi traffic tăng đột biến, và muốn thời gian khởi tạo mỗi instance nhanh nhất có thể.
**Đáp án đúng:** Tạo custom AMI (golden image) đã cài sẵn phần mềm/cấu hình, kết hợp Auto Scaling Group dùng AMI đó để launch instance mới.
**Vì sao:** Custom AMI loại bỏ thời gian cài đặt phần mềm qua User Data mỗi lần khởi tạo — instance mới sẵn sàng phục vụ ngay khi boot xong, phù hợp khi cần scale nhanh.

🧪 **Scenario 3 — Anti-pattern: over-provisioning vì sợ thiếu capacity**

**Tình huống:** Một đội kỹ sư lo ngại traffic tăng đột biến vào giờ cao điểm nên quyết định chạy cố định 20 instance kích thước lớn suốt ngày đêm, dù traffic thực tế buổi tối chỉ cần 3-4 instance.
**Đáp án đúng:** Dùng Auto Scaling Group với policy scale theo metric (VD: CPUUtilization hoặc request count qua CloudWatch alarm), để số lượng instance tự điều chỉnh theo tải thực tế.
**Vì sao đây là anti-pattern cần tránh:** Chạy cố định số lượng lớn instance để "phòng hờ" gây lãng phí chi phí phần lớn thời gian trong ngày — đúng mục tiêu của Auto Scaling là loại bỏ chính xác nhu cầu over-provisioning này mà vẫn đảm bảo đủ capacity khi cần.

## Key takeaways

- EC2 cho kiểm soát toàn bộ OS/runtime; chọn đúng purchasing option theo đặc tính workload (ổn định vs gián đoạn).
- Instance Store nhanh nhưng ephemeral; EBS bền vững hơn, tách rời vòng đời instance.
- Security Group là lớp bảo vệ đầu tiên, luôn áp dụng Least Privilege.
- ECS/Fargate và Lambda là compute alternative — chọn dựa trên mức độ container hoá và thời gian chạy của ứng dụng.

## Checklist tự ôn

- [ ] Tôi chọn đúng purchasing option cho ít nhất 3 kịch bản workload khác nhau.
- [ ] Tôi phân biệt được Instance Store và EBS về tính bền vững dữ liệu.
- [ ] Tôi giải thích được khi nào nên chọn EC2 thay vì Lambda/ECS/Fargate và ngược lại.
- [ ] Tôi hiểu Security Group là stateful, default-deny, chỉ allow rule.
